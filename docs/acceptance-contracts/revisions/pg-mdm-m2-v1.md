# Acceptance contract: pg-mdm M2 (policy intents, bindings, and receipts)

Contract revision: v1  
Source: `../pg-react/plans/PLAN_PG_MDM_STEWARDSHIP_INTEGRATION.md` §4 (`MDM-STEWARDSHIP/1`) and §5 M2; `plans/v0.14.md` (M2 implementation plan, start gate, binding model, APIs, receipts, action rules, restore, test matrix, exit criteria)  
Parent contract: None  
Parent snapshot: `contracts/MDM-STEWARDSHIP-1.json`, revision 1, SHA-256 `2161ce22b9d924ff3f3e6d8acde62fed01b6b1c1c4d7ba0fd4d5eb6e396e0fcf`  
Contribution: Implements M2 of `MDM-STEWARDSHIP/1`: bound automated queue assignment, due dates, escalation, and durable receipts.  
Prerequisites: M0 approved shared contract and fixtures (`plans/v0.12.md`); M1 v0.13 policy projection and passing real pg-react R1 read path (`plans/v0.14.md` start gate). The M2 implementation may proceed alongside pg-react R1 once M0 and M1 are complete.

Intended outcome: An authorized pg-react worker can submit only a fresh, policy-bound `ASSIGN_QUEUE`, `SET_DUE_AT`, or `ESCALATE` intent. pg-mdm either atomically applies one bounded control change and records its durable receipt, or returns the agreed terminal result without changing protected state. Retries and concurrent human or administrator changes cannot duplicate an action or overwrite newer authority.

## Unresolved gaps

- The source plan names joint M2 exit evidence through the actual React worker identity, but this checkout has no retrievable pg-react worker implementation or joint M2 fixture. MDM-local SQL evidence can cover database behavior; the cross-repository worker identity and work/receipt correlation remain a qualification dependency.

## Open questions

- M4 joint release qualification and showcase delivery.

- Identity decisions, MDM refresh/publication, and interpreting `APPLIED_CONTROL` as an identity outcome.
