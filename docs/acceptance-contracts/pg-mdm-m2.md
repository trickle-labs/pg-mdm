Intended outcome: An authorized pg-react worker can submit only a fresh, policy-bound `ASSIGN_QUEUE`, `SET_DUE_AT`, or `ESCALATE` intent. pg-mdm either atomically applies one bounded control change and records its durable receipt, or returns the agreed terminal result without changing protected state. Retries and concurrent human or administrator changes cannot duplicate an action or overwrite newer authority.

## Open questions

- None for M2 behavior. Exact API and race semantics are governed by approved `MDM-STEWARDSHIP/1` and `plans/v0.14.md`.

## Out of scope

- M1 policy projection work except as a prerequisite.
- M4 joint release qualification and showcase delivery.
- M3 human approval requirements; automatic `MATCH`/`NOT_MATCH`; direct merge/split; bulk actions; cross-database delivery; reviewer UI; business calendars; network delivery; generic action registry; new retry worker or command bus.
- Identity decisions, MDM refresh/publication, and interpreting `APPLIED_CONTROL` as an identity outcome.

## Change notes

- v2, authorized by the requesting contract owner on 2026-09-23. Affected IDs: R1, R2, R12, R13, R14. v1's binding administration and authority conflicted with the M2 plan. The approved parent v2 resolves this with entity-execution-role administration, bounded binding configuration, optimistic versions, and a safe legacy transition. Existing request encoding, intent outcomes, and action semantics are unchanged. v1 is preserved at `docs/acceptance-contracts/revisions/pg-mdm-m2-v1.md`.
- v3, authorized by the requesting contract owner on 2026-09-23. Affected ID: R1. v2 exposed `allowed_queues name[]` on Rust-facing create and replace APIs; v3 uses `text[]`, validates the values, and persists canonical queue names to the same durable `name[]` column. This matches pgrx's `Vec<String>` SQL mapping and avoids decoding PostgreSQL's fixed-width `name` values as varlena text. v2 is preserved at `docs/acceptance-contracts/revisions/pg-mdm-m2-v2.md`.
