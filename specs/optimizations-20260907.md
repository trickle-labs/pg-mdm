# Refresh bottlenecks and optimization backlog

Status: proposed work for later implementation. This review changed no runtime code and ran no new benchmarks.

Review reference: commit `7645293`, pg_mdm 0.14.1. File and function references below describe that revision.

## Main finding

Small updates still trigger substantial whole-entity work. The largest opportunities are restoring proven affected resolution, batching publication writes, and removing repeated membership scans. Graph refresh and publication dominate the retained synthetic measurements.

## Retained measurements

Retained evidence: [v0.14 operating-envelope evidence](../evidence/v0.14/docker-e2e-envelope.json), generated by [the incremental qualification workload](../tests/incremental_qualification.sql).

| Records | Total refresh p95 | Graph refresh p95 | Resolution p95 | Publication p95 |
| ---: | ---: | ---: | ---: | ---: |
| 128 | 773.470 ms | 679.700 ms | 5.000 ms | 65.550 ms |
| 2,048 | 1,969.001 ms | 1,007.100 ms | 75.100 ms | 850.300 ms |

Each population has five warmups and 30 measured samples. Each sample updates one source record and reports two delta rows. The suite compares the complete public publication with an administrative full rebuild after every sample, including warmups: 70 equivalence checks in total.

Limitations:

- These are retained observations, not a fresh profile or production capacity measurements.
- The workload uses synthetic exact-email records; it does not exercise dense matching blocks or large connected components.
- The retained environment runs an amd64 Docker image on an arm64 Docker engine.
- Each stage's p95 is calculated independently; the stage percentiles do not form an additive breakdown of total p95.
- The qualification SQL expects full resolution after steady-state mutations. These timings do not establish affected-resolution performance.
- The current qualification SQL, operating-envelope SQL, and Cargo.lock hashes match the hashes recorded in the evidence. That check alone does not establish identical runtime source or environment.

## 1. Restore affected resolution for steady-state changes

**Priority:** high; broadest potential impact, with the invalidation cause still to be established.

The qualification workload expects `resolver_strategy = 'full'`, `resolver_fallback_reason = 'delta_full_invalidation'`, and an affected-record count equal to the entire population after each one-record update. The [README](../README.md) describes this workload as measuring affected refreshes, so the documentation and qualified behavior disagree.

In [refresh.rs](../src/api/refresh.rs), `persist_refresh_inner` excludes affected evaluation whenever either terminal delta consumer reports full invalidation. Declaring graph nodes `DIFFERENTIAL` does not establish that terminal consumers produce usable exact deltas.

Proposed action:

- Identify whether the evidence or golden consumer emits `FULL_INVALIDATION`; record the producer's effective graph mode and invalidation cause.
- Resolve the graph or upstream delta limitation so ordinary supported mutations produce proven `EXACT` ranges.
- Update qualification expectations and documentation once affected execution is demonstrated.

Validation: assert the complete refresh result for steady-state changes, including affected scope, strategy, fallback reason, and zero delta lag. Compare complete public output with a full rebuild after every mutation. Preserve full fallback for invalidations, gaps, contract changes, resnapshots, and uncertain limits; do not bypass completeness checks.

## 2. Batch publication writes

**Priority:** high; strongest local target in the measured workload.

In [refresh.rs](../src/api/refresh.rs), `persist_refresh_inner`, `persist_publication_snapshots`, and `persist_outputs` issue separate SQL calls for individual identities, memberships, golden values, and output rows. For a full refresh with N singleton identities and one golden field, the five main insert/upsert loops issue approximately 5N calls: 10,240 at N = 2,048, before other publication work.

Publication p95 grows from 65.550 ms to 850.300 ms across the measured populations. The loops are a concrete optimization opportunity, but their individual contribution to that timing has not been profiled.

Proposed action:

- Replace row-at-a-time writes with bounded batches using set-based `INSERT ... SELECT` and upserts; reuse existing JSONB handling where practical.
- Preserve existing conditional updates, conflict handling, quoting, type conversion, and transaction boundaries.
- Replace full-path row-at-a-time stale-output deletion with a set-based anti-join where profiling justifies it.

The entity-output change predicate includes `last_change_revision`, so a new full publication can update rows whose other values remain unchanged. Confirm the revision contract before changing that behavior.

Validation: compare complete publications, provenance, identity ledgers, reviews, and revision fields before and after batching. Retain rollback behavior and acknowledge delta batches only after successful publication. Measure publication latency and SQL-call volume on the same workload and environment.

## 3. Remove quadratic membership scans

**Priority:** high; small, contained local changes.

Two paths repeatedly scan the entire membership collection:

- [evaluation.rs](../src/evaluation.rs), `select_golden`: finds a membership's source sort key for every golden row, despite already building a record lookup.
- [refresh.rs](../src/api/refresh.rs), `persist_outputs`: filters all memberships for every active identity to calculate member count.

With one golden row and one identity per source record, both patterns perform quadratic membership work during full evaluation/publication.

Proposed action: retain the required membership data in a record lookup and calculate member counts by identity in one pass. Reuse the existing `BTreeMap` approach; no new dependency or cache is required.

Validation: verify complete golden selections, provenance, output rows, and deterministic ordering. Exercise multiple members per identity and inactive memberships as well as singleton records. Measure full refreshes over increasing populations to check that these scans no longer grow quadratically.

## 4. Reduce source synchronization work

**Priority:** medium; measure separately before changing the source-capture path.

In [refresh.rs](../src/api/refresh.rs), `grant_refresh_access` scans all active source keys into snapshots. `sync_source_records` then reconciles those complete snapshots, and `refresh_graph` reconciles the graph helper tables. This work occurs before the empty-delta shortcut, so a no-change refresh still pays source reconciliation costs.

Source scanning in `grant_refresh_access` also happens before `persist_refresh_inner` starts its operation timer. Source synchronization occurs before the graph-stage timer. The existing stage timings therefore do not isolate these costs.

Proposed action:

- Measure access setup, source scanning, source-record synchronization, graph helper synchronization, and end-to-end refresh separately.
- Investigate changed-key synchronization only when source capture provides a complete, trustworthy change range.
- Retain complete scans for bootstrap, recovery, resnapshot, and unsupported source shapes. Preserve caller access checks and entity-wide resource limits.

Validation: compare exact source-record registration and active state, plus complete public outputs, across insert, update, delete, soft delete, reactivation, no-change, and recovery cases. Measure both no-change and small-update refreshes.

## 5. Reduce global work inside affected refreshes

**Priority:** medium; pursue after affected execution and simpler local improvements.

In [refresh.rs](../src/api/refresh.rs), `evaluate_affected` loads all previous identity state, reviews, golden provenance, and resolution facts before selecting the affected scope. It also loads all overrides before filtering them. This retains whole-entity decoding and memory costs even when the resolver handles a small component.

`persist_publication_snapshots` copies unchanged golden provenance to each new revision. It also reconstructs and numbers the complete resolution-fact snapshot. Publication therefore retains global copying costs and growing historical storage. The result digest is calculated from the complete merged semantic publication, which is another global cost.

Proposed action:

- Measure state loading, merged-state construction, digest generation, and snapshot copying separately.
- Fetch state by affected records and identities where sufficient information can be obtained without weakening closure or identity-continuity checks.
- Consider a different historical representation only if snapshot copying remains a dominant cost after batching. Preserve exact historical explanation behavior and deterministic digest semantics.

Validation: compare complete current and historical publications, including aliases, splits, retirements, reviews, provenance, and result digests. Do not claim end-to-end cost proportional to the delta while a whole-publication digest or snapshot copy remains.

## 6. Avoid repeated candidate generation

**Priority:** workload-dependent; investigate dense candidate blocks.

In [graph_spec.rs](../src/graph_spec.rs), `candidate_pair_stats_sql_with_relation` wraps the same self-join and deduplication query generated for candidate pairs. Separate graph nodes therefore contain repeated candidate-generation work. The retained unique-email workload does not quantify its cost.

Proposed action: profile both nodes on representative dense blocks and overlapping channels. Investigate sharing the deduplicated result while preserving the graph's dependencies, overflow checks, and exact candidate completeness.

Validation: compare the complete candidate-pair set and overflow outcomes for exact, composite, prefix, token, and overlapping channels. Do not replace exact cross-channel counts with estimates or silently skip oversized work.

## 7. Skip empty cannot-link checks

**Priority:** small opportunistic improvement for larger components.

In [resolver.rs](../src/resolver.rs), `cannot_cross` checks the cross-product of component members even when the cannot-link set is empty. The cost increases with component size; it is not represented by the retained singleton workload.

Proposed action: return immediately when the cannot-link set is empty. Consider adjacency-based checks only if non-empty constraint checking later proves expensive.

Validation: compare complete resolver results and explanations with the existing oracle for both empty and non-empty constraints. Include a prohibited cross-component merge; preserve all contradiction handling.

## Delivery order and measurement plan

1. Capture a reproducible baseline and identify the terminal full-invalidation producer.
2. Batch publication writes and remove quadratic membership scans as separate, reviewable changes.
3. Restore and qualify affected resolution when the invalidation cause is resolved.
4. Use measured stage costs to prioritize source synchronization, scoped state loading, and historical copying.
5. Profile dense workloads before redesigning candidate generation or constraint indexing.

Use the existing complete-publication/full-rebuild comparison as the primary correctness check. Any added regression checks must verify exact outputs rather than counts alone. Use appropriate existing unit/property tests for algorithm changes and database E2E checks for publication, source capture, and delta handling.

For performance comparisons, retain warmup/sample counts, population, changed-record count, candidate density, component sizes, stage timings, architecture, and resource limits. Repeat the 128- and 2,048-record workloads first, then add a representative larger workload, a no-change refresh, and dense matching cases. Choose timing targets after establishing a reproducible baseline; the retained p95 values are observations, not acceptance thresholds.

No optimization here authorizes changing matching completeness, deterministic ordering, identity continuity, historical explanations, security checks, resource-limit enforcement, atomic publication, or delta acknowledgement behavior.
