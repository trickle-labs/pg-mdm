# v0.15 implementation plan: joint stewardship qualification

## Outcome

Complete M4 with pg-react R5. Qualify queue assignment, due dates, and bounded
escalation on one named cohort using the real packaged extensions. Publish the
supported limits, recovery procedure, and exact evidence.

This release contains no new MDM behavior unless a qualification failure requires
a correctness fix. A fixture demonstration, release tag, or successful enqueue
does not close M4.

## Start gate

Require MDM v0.13 and v0.14 acceptance, React R0 through R3, and one common
PostgreSQL 18 image with pg-trickle 0.105.3. Record the exact MDM and React commits,
package digests, `MDM-STEWARDSHIP/1` digest, fixture digest, worker role, trigger
capture, scheduler state, transaction isolation, and FULL fallback state.

Name the initial cohort before testing. Record its case categories, queues, due
policy, escalation levels, expected arrival and churn, manual-edit patterns,
retention need, and recovery objective. Do not infer broad production support
from this cohort.

## Shared demonstration

Maintain the runnable demonstration in pg-react at
`showcase/mdm-stewardship/`. Reuse its immutable fixtures in the MDM release
suite rather than copying expected values by hand.

The demonstration must:

1. Publish one ambiguous MDM review occurrence.
2. Let React select and submit an allowed queue and due time.
3. Assert the exact canonical request bytes, MDM receipt, control row, and React
   work outcome.
4. Advance managed time without source-table writes and escalate exactly one
   permitted level.
5. Retry the same work and preserve the original deadline and level.
6. Accept a human `MATCH` or `NOT_MATCH` through the existing authenticated MDM
   API.
7. Refresh MDM independently and close the review only after successful
   publication.

No React consequence may call `mdm.refresh()`. No worker grant may reach a human
decision, golden override, merge, split, helper, or private table.

## Qualification matrix

Run these cases through the actual React worker identity and public MDM API:

| Case | Required result |
|---|---|
| Tied routing candidates | Ambiguous React result and no MDM intent |
| Missing routing candidate | Manual path remains available; no fabricated queue |
| Duplicate and uncertain delivery | One control and one receipt |
| Changed evidence or definition | Old work is stale and is reevaluated |
| Concurrent human assignment | Manual protection wins |
| Recurring review | New case and request keys; old work cannot act |
| Time-only deadline | Evaluation runs without business-source changes |
| Repeated escalation | One applied change per occurrence and level |
| Binding pause | No new intent passes the acknowledged barrier |
| Policy replacement | Old work fails; new binding starts inactive |
| Missing capability | Effects stop before mutation |
| Privilege revocation | No receipt or case details leak |
| Publication failure after human decision | Prior outputs remain; pending state stays truthful |
| Restart | Original keys, controls, due time, and receipts remain |
| Adjacent upgrade | Existing work and MDM state remain correlated |
| Logical restore | Automation stays disabled until explicit reconciliation |
| Physical clone | Database identity guard prevents writes |
| FULL fallback | Shared-source results remain complete and strategy is visible |

For every case compare full policy rows, request bodies, receipts, work outcomes,
and final review state. Count-only assertions are insufficient.

## Shadow and enablement

Cover one fixed population with React's bounded side-effect-free comparison.
Record the chosen publication boundary and prove that every case appears exactly
once. A partial comparison does not authorize the cohort.

Use these stages:

1. Install both extensions with the policy binding inactive.
2. Grant the read-only projection and run the complete shadow comparison.
3. Have the workload owner approve exact routes, deadlines, protected cases,
   ambiguous cases, and exceptions.
4. Activate queue and due-date actions for the named cohort.
5. Activate escalation only after real time-only tests pass.
6. Observe the predeclared period and accept or reject the supported profile.

Increasing the cohort or action list is a new binding review. Pause blocks new
intents but never reverses an accepted human directive or published identity.

## Operations and limits

Provide ordinary SQL queries for:

- stale, denied, invalid, and conflicting intent rates with denominators;
- overdue open cases and the oldest due time;
- pending, leased, retrying, and held React work;
- repeated attempts for the same occurrence and escalation level;
- accepted controls and human decisions not yet reflected by MDM publication;
- active versus paused or invalid MDM binding runtime state; and
- request and receipt coverage for the shared audit horizon.

Measure no-change cycles, steady arrivals, bursts, one hot case, time-only expiry,
backlog drain, restart, restore, and clone startup. Record rows, writes, WAL,
storage, latency, failures, CPU, memory, and exact configuration. Freeze numeric
limits before the final run. Missing data is not a zero value.

Keep receipts indefinitely because v0.14 has no pruning contract. Report their
measured growth and the cohort ceiling. Add retention controls only after both
projects agree on an out-of-horizon protocol.

## Recovery drills

- Pause the binding and cross its acknowledged runtime-version barrier before an
  upgrade or restore.
- Back up one coherent database state and retain matching extension packages.
- Test a failed adjacent upgrade without relying on a reverse migration.
- Restore into new role and relation OIDs, run MDM rebind, reconcile the React
  package and pending work, then activate a new binding runtime explicitly.
- Start a physical clone with copied rows and prove that the database OID guard
  blocks intent acceptance.
- Verify that old receipts remain readable to the authorized role before new
  work resumes.

## Release evidence

Store a machine-readable qualification manifest with each gate's name, command,
commit, package and fixture digests, start and finish times, expected result,
actual result, retained log, and reviewer. Derive the overall result from the
blocking gates. Do not convert skipped, fixture-only, or missing evidence into a
pass.

The release notes state the exact cohort, numerical limits, known FULL nodes,
retention behavior, recovery steps, and opt-in status. They must also state that
approvals, identity automation, RLS policy sources, multiple scopes, and network
delivery remain unsupported.

## Implementation order

1. Freeze the final four-package manifest and shared fixture digest.
2. Run the shared failure and authorization matrix before any live effects.
3. Complete populated upgrade, restore, restart, and clone drills.
4. Run the complete fixed-population shadow and obtain workload-owner approval.
5. Enable routing and deadlines, then bounded escalation, for the named cohort.
6. Measure the declared observation period and limits.
7. Package 0.15.0 only after joint and independent sign-off.

## Exit criteria

- [ ] The shared demonstration passes with exact requests, receipts, controls,
  work outcomes, and final publication state.
- [ ] No worker path can call a human or identity-changing API.
- [ ] Duplicate, stale, paused, replaced, unauthorized, restored, and cloned work
  fails with the required outcome and no extra control.
- [ ] The fixed-population shadow has complete coverage and owner approval.
- [ ] The named cohort stays inside frozen latency, backlog, storage, and recovery
  limits for the declared observation period.
- [ ] Operators can inspect and recover every supported failure through ordinary
  public interfaces.
- [ ] Both release owners and the independent reviewer sign the exact manifest.

## Deferred

Do not add approval requirements, automatic identity actions, more scopes, RLS
policy inputs, external delivery, or a reviewer UI. M3 remains optional. v0.16
returns to MDM-only work and has no runtime dependency on pg-react.
