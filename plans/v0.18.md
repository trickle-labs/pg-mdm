# v0.18 implementation plan: semantic change feed

## Outcome

Add an opt-in ordinary PostgreSQL change table for each entity. Generate ordered
semantic events from the same before-and-after state used by publication, and
commit the events with the current output tables.

Ship SQL cursor replay, gap detection, and snapshot resynchronization with the
feed. External transport remains outside MDM.

## Start gate

Require the v0.16 publication comparison path and v0.17 merge and split semantics.
The feed may describe only behavior implemented by the installed extension. Do
not emit placeholder events for locks, approvals, or move-member commands that do
not exist.

## Enablement and output tables

Add:

```text
mdm_admin.enable_change_feed(entity_name text, expected_publication_revision bigint)
    -> enabled_revision bigint, output_name name

mdm.change_feed_status(entity_name text, after_revision bigint,
                       after_event_no integer)
    -> status text, earliest_revision bigint, latest_revision bigint,
       snapshot_revision bigint
```

Enablement is explicit and irreversible in this release. It reserves and creates
`mdm_out.<entity>_changes` plus `mdm_out.<entity>_change_details` in one
transaction, records the current publication as `enabled_revision`, and writes an
operation. It does not synthesize history before that revision.

Extend `output_names.output_kind` with `changes` and `change_details`. Create both
tables through the existing output DDL and ownership path. Do not grant access to
`PUBLIC`; operators grant consumers `SELECT` explicitly.

`mdm_out.<entity>_changes` has:

```text
event_id                    uuid unique not null
publication_revision       bigint not null
event_no                    integer not null, positive
event_type                  text not null
affected_mdm_ids            uuid[] not null
source_record_ids           uuid[] not null
field_name                  name null
reason_code                 text not null
operation_id                uuid not null
directive_ids               uuid[] not null
semantic_versions           jsonb not null
before_digest               bytea null
after_digest                bytea null
detail_ref                  uuid null
payload                     jsonb not null
created_at                  timestamptz not null
primary key (publication_revision, event_no)
```

`payload` contains bounded, masked metadata only. It must not contain raw golden
values, source keys, unmasked review subjects, policy request bodies, or private
graph names. Keep every array canonical and duplicate-free.

Store large member sets in `mdm_out.<entity>_change_details` as ordered chunks:

```text
detail_ref                  uuid not null
chunk_no                    integer not null, positive
source_record_ids           uuid[] not null
primary key (detail_ref, chunk_no)
```

Each chunk stays under a fixed row-byte and member-count limit. The event payload
states the total member count and chunk count. Details have the same access and
retention as their event.

## Event model

Implement these event types because their source state exists by v0.17:

```text
ENTITY_CREATED
ENTITY_REACTIVATED
ENTITY_RETIRED
ENTITY_MERGED
ENTITY_SPLIT
MEMBER_ADDED
MEMBER_REMOVED
MEMBER_MOVED
GOLDEN_VALUE_CHANGED
GOLDEN_OVERRIDE_CHANGED
REVIEW_OPENED
REVIEW_REOPENED
REVIEW_RESOLVED
IDENTITY_ALIAS_CHANGED
```

Generate events directly from the old and proposed `Evaluation` states. Do not
infer them later from physical output-table changes. Use newly accepted directive
and override references only as causes; an accepted control-plane write emits no
event until refresh publishes a semantic effect.

One high-level merge or split event summarizes the identity transition. Member
events remain separate so consumers can maintain a member index. A merge names
one canonical successor and all retired IDs. A split names the parent and every
successor, with complete member assignment in the event or detail rows.

Emit `GOLDEN_VALUE_CHANGED` when the typed value, status, winner, or provenance
changes. Emit `GOLDEN_OVERRIDE_CHANGED` only when an override changes the
published golden result or provenance. Emit review events from occurrence state:
first occurrence is opened, a later occurrence is reopened, and an open-to-closed
transition is resolved.

## Deterministic identity and order

Create a pure `changes::diff(old, new, causes)` function. Assign event-type ranks
in the order listed above. Sort candidate events by rank and then canonical
subject bytes. The broader order remains:

1. entity lifecycle and continuity;
2. membership;
3. golden values and overrides; and
4. reviews.

Assign `event_no` after sorting. Generate `event_id` with PostgreSQL `uuidv7()`
when the publication transaction persists the ordered event. A rolled-back ID is
not observable. A committed event ID never changes.

Hash each protected before and after value with a versioned domain tag. Include
semantic policy versions and the publication operation ID. The complete ordered
event set contributes to the publication result digest when the feed is enabled.

## Publication rules

Run semantic diff after `Evaluation` and before deciding whether the refresh
changed. For a feed-enabled entity:

- advance the publication revision when primary outputs, durable semantic state,
  or the event set changes;
- insert events and detail rows in the same transaction as identity, membership,
  golden, review, and public output writes;
- emit no event and do not advance the revision for an observation-only refresh;
  and
- roll back the entire publication when any event or detail insert fails.

A retry after rollback recomputes the same ordered event content at the same next
revision. It may allocate different uncommitted UUIDs, but it cannot create a
duplicate committed semantic event. A retry after commit observes no new semantic
diff and emits nothing.

Entities without an enabled feed keep v0.17 publication behavior and output
shape. Enabling one entity never adds a core dependency for another.

## Cursor replay and resynchronization

Consumers read with ordinary SQL:

```sql
SELECT *
FROM mdm_out.customer_changes
WHERE (publication_revision, event_no) > ($1, $2)
ORDER BY publication_revision, event_no
LIMIT $3;
```

`change_feed_status()` returns:

- `CURRENT` when the cursor equals the latest retained event position;
- `READY` when later retained events can be replayed; or
- `GAP` when the cursor predates feed enablement or any retained start.

Reject negative event numbers and cursors ahead of the current publication.
Authorize the call only when the selected role can read both feed tables. Status
must not disclose entity or retention metadata to another role.

The first release performs no automatic event deletion. Its retention promise is
all committed events and detail rows since `enabled_revision`. Manual deletes are
unsupported. Gap detection still treats a cursor before enablement, missing first
revision, or inconsistent detail reference as `GAP` and reports the current
snapshot revision.

To resynchronize, begin a `REPEATABLE READ` transaction, call
`change_feed_status()`, record `snapshot_revision`, read the entity, members, and
review tables in the same snapshot, then set the replacement cursor to
`(snapshot_revision, 2147483647)`. Document this exact sequence and test a
concurrent publication. Do not add consumer registration or cursor tables until a
named consumer needs MDM to own cursor state.

## Restore, clone, and lifecycle

Register feed enablement metadata, events, and detail rows for logical dump.
Extend `configure_helper.sql`, `drop_entity()`, output ownership checks, and clone
tests for both new output kinds. Restore preserves event IDs and order, but the
consumer must still compare its cursor with `change_feed_status()`.

Dropping an entity removes its feed tables through the existing confirmed
lifecycle transaction. A failed drop leaves both tables and metadata intact.
There is no disable-and-delete API in this release.

## File layout

```text
src/
  changes.rs               pure semantic diff, ordering, and digests
  output.rs                change and detail table definitions
  api/changes.rs           enablement and status APIs
  api/refresh.rs           atomic event persistence
  api/lifecycle.rs         feed cleanup with entity deletion
  schema.rs                enablement metadata and output-name kinds
  error.rs                 feed, cursor, detail, and retention codes
tests/
  change_tests.rs          pure before-and-after fixtures
  fixtures/changes_v1.json
  e2e_changes.sql          publication, replay, rollback, restore, and grants
```

Reuse `Evaluation`, `operations`, output-name reservation, digest helpers, and
public output DDL. Do not add an outbox service or transport abstraction.

## Implementation order

1. Freeze event payloads, ordering, digests, and before-and-after fixtures.
2. Implement the pure semantic diff and complete event-type tests.
3. Add explicit feed enablement and the two public output tables.
4. Persist events and details inside the publication transaction.
5. Add status, replay, and snapshot-resynchronization tests.
6. Extend entity drop, upgrade, restore, clone, ACL, and package checks.
7. Add the `0.17.0` to `0.18.0` migration, archive, documentation, and supported
   storage envelope.

## Test matrix

| Case | Required result |
|---|---|
| Entity creation, retirement, reactivation | Exact lifecycle event and order |
| Merge | Canonical successor, every retired ID, causes, and member moves |
| Split | Parent, every child, and complete member assignment |
| Member add, remove, move | Exact source record and before and after digests |
| Golden or provenance-only change | One bounded golden event |
| Review open, recur, resolve | Correct occurrence event type |
| No-op refresh | No event and no publication advance |
| Rollback after event insert | No output, event, detail, or revision change |
| Retry after rollback or commit | One committed semantic event set |
| Unauthorized consumer | No event or detail disclosure |
| Cursor before enablement | `GAP` with snapshot revision |
| Concurrent snapshot resync | Coherent outputs and resume cursor |
| Large split | Bounded event plus complete ordered detail chunks |
| Upgrade and restore | Exact IDs, order, details, grants, and feed start survive |
| Clone | Isolated future publications with retained prior history |

Property-test event order against shuffled input collections. The serialized
event content and event numbers must remain identical.

## Exit criteria

- [ ] Events come from semantic before-and-after state and commit with outputs.
- [ ] `(publication_revision, event_no)` is complete, unique, and deterministic.
- [ ] Every implemented merge, split, lifecycle, membership, golden, and review
  transition has an exact fixture.
- [ ] Observation-only refreshes emit no event.
- [ ] Payloads are bounded and protected; large member sets remain complete in
  retained detail rows.
- [ ] Replay, gap detection, and snapshot resynchronization work through ordinary
  SQL under concurrent publication.
- [ ] Rollback, retry, authorization, upgrade, restore, clone, and entity drop
  pass in the cumulative E2E suite.

## Deferred

Do not add pg-tide delivery, webhooks, consumer-owned cursor registration,
automatic retention, event compaction, resolved entities as sources, or event
types for unavailable features. Add transport only when a consumer needs more
than ordinary SQL or logical replication.
