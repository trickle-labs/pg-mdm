# v0.4 implementation plan: candidate generation

## Outcome

Enumerate every source-record pair admitted by the definition's exact, composite, prefix, and token predicates. Canonicalize and deduplicate pairs across channels. Reject an oversized block or aggregate candidate set before returning any result.

The release proves completeness against an all-pairs oracle on generated small datasets. It does not run an all-pairs query in production and does not execute a `pg_trickle` graph.

## Prerequisites and dependency changes

Start from v0.3 with normalized `value` rows and stable source-record sort keys. Candidate code must ignore every non-value state.

Add `proptest` as a development dependency. Add no runtime crate. Use `BTreeMap` and `BTreeSet` for deterministic grouping, ordering, and deduplication. Use the existing `sha2` dependency only to create non-sensitive block digests for errors.

Add the 0.3.0 to 0.4.0 extension migration and archive the generated 0.4.0 install SQL. The migration may contain only function replacements and version metadata if no durable table changes are needed.

## Data and schema skeleton

Do not add a durable production table. Model the future derived relation with Rust records and temporary test tables:

```rust
pub(crate) struct NormalizedRecord {
	pub source_record_id: pgrx::Uuid,
	pub source_sort_key: Vec<u8>,
	pub field: String,
	pub normalized: String,
	pub canonical_bytes: Vec<u8>,
}

pub(crate) struct CandidatePair {
	pub left_source_record_id: pgrx::Uuid,
	pub right_source_record_id: pgrx::Uuid,
	pub left_sort_key: Vec<u8>,
	pub right_sort_key: Vec<u8>,
	pub discovery_channels: Vec<String>,
}

pub(crate) struct CandidateLimits {
	pub max_block_records: usize,
	pub max_candidate_pairs: usize,
}
```

The compiled graph-spec stages have these logical row shapes:

```text
candidate block:
  channel_id, block_key, source_record_id, source_sort_key

canonical candidate pair:
  left_source_record_id, right_source_record_id,
  left_sort_key, right_sort_key, discovery_channels
```

Order each pair by `source_sort_key`, not by UUID. Require different source-record IDs and emit one row per logical pair. Sort `discovery_channels` by stable channel ID.

## Candidate channel contract

Compile these V1 channels:

| Channel | Block membership |
|---|---|
| `exact` | One normalized field has identical canonical bytes |
| `composite_exact` | Every named field is `value`, and the ordered tuple of canonical bytes is identical |
| `prefix` | The first configured number of Unicode scalar values is identical after normalization |
| `token` | At least one configured token from the normalized value is identical |

The token channel splits on normalized whitespace, rejects tokens below the configured minimum scalar length, removes duplicate tokens within one record, and sorts the rest by UTF-8 bytes. It does not stem words, remove language-specific stop words, or use approximate retrieval.

An identity or strong match may own a channel. A supporting match may be evaluated for an already discovered pair but cannot own a channel. A fuzzy match must name at least one complete channel unless another identity or strong rule already discovers the same needed pairs through explicit compiled lineage.

The expanded definition stores `max_block_records`, `max_candidate_pairs`, and `warning_block_records`. Before implementation, choose measured positive defaults in `src/semantics.rs`, record them in the semantic manifest, and document the tested operating envelope. A definition may lower a limit. Raising a limit above the compiled absolute ceiling requires an extension upgrade, not an unchecked per-entity override.

## Completeness algorithm

For each channel:

1. Build the full block key for every eligible normalized record.
2. Group records by the full key. Never group by a digest alone.
3. Sort members by `source_sort_key` and reject duplicate sort keys.
4. If a block exceeds `max_block_records`, return `MDM_CANDIDATE_BLOCK_LIMIT` with the channel, SHA-256 block digest, cardinality, and configured limit.
5. Compute `n * (n - 1) / 2` with checked arithmetic before allocating pairs.
6. Enumerate all pairs in the accepted block and insert them into one ordered set.
7. If the ordered set would exceed `max_candidate_pairs`, return `MDM_CANDIDATE_TOTAL_LIMIT` and discard the in-memory result.
8. Add the channel ID to an existing pair when another channel discovers it.

Because callers receive a result only after all channels succeed, an error cannot expose a partial candidate set. The later refresh transaction also rolls back any derived work.

## API skeleton

Add no public SQL function. Extend the internal Rust API:

```rust
pub(crate) fn generate_candidates(
	plan: &CandidatePlan,
	values: &[NormalizedRecord],
	limits: CandidateLimits,
) -> Result<Vec<CandidatePair>, MdmError>;

#[cfg(test)]
pub(crate) fn all_pairs_oracle(
	plan: &CandidatePlan,
	values: &[NormalizedRecord],
) -> Vec<CandidatePair>;
```

Under the `pg_test` feature, expose a JSONB fixture wrapper for end-to-end limit and SQL-stage tests. Omit the wrapper and the all-pairs oracle from release packages.

Extend `mdm.describe()` with the logical channel ID, channel kind, fields, parameters, owning rules, warning threshold, hard block limit, and aggregate pair limit. Do not expose generated private relation names.

The graph-spec compiler emits ordinary relational SQL for each block stage and one pair-union stage. Each stage retains the full block value for equality and a digest only for diagnostics. v0.8 decides physical indexes after `pg_trickle` accepts the graph.

## Implementation order

1. Freeze the channel JSON format, stable channel IDs, and limit fields.
2. Implement canonical pair keys and checked pair-count arithmetic.
3. Implement exact and composite channels.
4. Implement prefix and token channels.
5. Add cross-channel union, deduplication, and completeness errors.
6. Write the test-only all-pairs oracle and generated comparisons.
7. Emit deterministic block and pair stages in `graph_spec.rs`.
8. Extend `describe`, the operating-envelope documentation, migrations, and upgrades.

## Test matrix

| Level | Case | Expected result |
|---|---|---|
| Unit | Exact values with null and non-value states | Only equal `value` rows share a block |
| Unit | Composite channel with one absent member | The record joins no composite block |
| Unit | Prefix length at zero, at value length, and above value length | Validation rejects zero; the other cases are deterministic |
| Unit | Repeated tokens within one record | No self-pair or duplicate pair is emitted |
| Unit | One pair found by several channels | One pair contains sorted unique channel IDs |
| Unit | UUID order differs from source sort order | Left and right follow source sort order |
| Unit | Block at and one over the hard limit | The first completes; the second returns `MDM_CANDIDATE_BLOCK_LIMIT` |
| Unit | Aggregate pair count at and one over its limit | The first completes; the second returns `MDM_CANDIDATE_TOTAL_LIMIT` |
| Unit | Pair-count arithmetic near `usize` overflow | Checked arithmetic returns a limit error without allocation |
| Property | Random small records and channel plans | Generated candidates equal the all-pairs oracle |
| Property | Shuffle records, fields, and channel evaluation order | The result bytes remain identical |
| Property | Add duplicate discovery channels | Pair membership stays unchanged |
| End to end | Compile one channel of every kind | Graph-spec stage SQL parses on PostgreSQL 18 |
| End to end | Cause a block overflow in a temporary fixture relation | No candidate result table or operation success row remains |
| Upgrade | Upgrade every prior archived release | Definitions, source identities, and digests remain unchanged |

## Exit criteria

- [ ] Every V1 channel has a frozen JSON contract, version, and fixture case.
- [ ] Generated small datasets match the all-pairs oracle.
- [ ] Input order, plan order, UUID order, and PostgreSQL collation do not change candidate bytes.
- [ ] A hard block or aggregate limit returns a stable error and no partial result.
- [ ] Supporting evidence cannot create a candidate channel.
- [ ] `mdm.describe()` reports the complete logical plan and all warning and hard limits.
- [ ] Every generated stage parses on PostgreSQL 18 and names only public functions in the `pgtrickle` schema.
- [ ] The measured defaults and absolute ceilings are positive, documented, and included in the semantic manifest.
- [ ] Upgrade tests and the complete v0.1 through v0.3 matrices pass.

## Deferred

Do not add phonetic indexes, trigram indexes, locality-sensitive hashing, nearest-neighbor search, adaptive truncation, or plan-dependent sampling. Add a new channel only when its complete logical predicate and hard failure behavior are specified.
