# v0.6 implementation plan: conservative clustering

## Outcome

Implement the executable full-reference resolver for V1 clustering. It applies manual match closure, component-level cannot-links, authority conflicts, and the one conservative component-admission policy in a total order. It returns complete memberships plus accepted and rejected union facts for later identity, review, and explanation work. A separate set-based small-graph oracle checks the production union-find implementation.

The resolver does not allocate `mdm_id` values or publish output tables. v0.7 owns identity continuity and publication shapes.

## Prerequisites and dependency changes

Start from v0.5 with canonical source-record sort keys, coherent steward decisions, deterministic pair decisions, ordered automatic edges, authority facts, and grouped evidence.

Add no runtime or development dependency. Use `Vec`, `BTreeMap`, and `BTreeSet`. Implement union-find locally because the resolver must merge component metadata and return deterministic reasons, which a generic crate does not provide.

Add the 0.5.0 to 0.6.0 migration and archive the 0.6.0 install SQL. No durable schema addition is expected.

## Data and schema skeleton

Add no durable production table and no public SQL function. Use these internal records:

```rust
pub(crate) struct ResolverInput {
	pub records: Vec<ResolverRecord>,
	pub manual_matches: Vec<ManualEdge>,
	pub cannot_links: Vec<CannotLink>,
	pub pair_decisions: Vec<PairDecision>,
	pub limits: ResolverLimits,
}

pub(crate) struct Membership {
	pub source_record_id: pgrx::Uuid,
	pub source_sort_key: Vec<u8>,
	pub component_key: Vec<u8>,
}

pub(crate) struct UnionFact {
	pub left_component_key: Vec<u8>,
	pub right_component_key: Vec<u8>,
	pub edge: PairKey,
	pub outcome: UnionOutcome,
	pub reason_code: String,
	pub evidence_groups: Vec<String>,
}

pub(crate) struct Resolution {
	pub memberships: Vec<Membership>,
	pub accepted: Vec<UnionFact>,
	pub rejected: Vec<UnionFact>,
}

```

The `component_key` is the smallest member `source_sort_key`. It is a deterministic result key for tests and v0.7 reconciliation, not a public entity ID.

Extend the expanded entity limits with positive, versioned values for maximum active records, automatic edges, records per component, and component checks. Measure and document the defaults before release. Crossing any hard limit returns an error and no `Resolution`.

## API skeleton

The release adds one internal entry point and no public SQL function:

```rust
pub(crate) fn resolve(input: ResolverInput) -> Result<Resolution, MdmError>;
```

Extend `mdm.describe()` with clustering policy version 1, the component-admission table, and every resolver limit.

Under the `pg_test` feature, expose a JSONB fixture wrapper around `resolve` for PostgreSQL end-to-end tests. Omit it from release packages.

Keep the oracle behind `cfg(test)`. It represents components as ordered sets and applies the contract directly after each edge. It does not call union-find, component metadata merge code, production admission helpers, or production serialization. Limit it to small graphs where exhaustive set operations are cheap.

## Resolution algorithm

Run these steps in order:

1. Validate that record IDs and source sort keys are unique and that every edge endpoint exists.
2. Sort records by source sort key and create one component per record.
3. Load every cannot-link as a symmetric component constraint.
4. Sort manual matches by canonical endpoint keys and union them.
5. Abort if the manual closure contains a cannot-link. v0.5 prevents this state, but the resolver treats persisted inconsistency as fatal.
6. Sort automatic edges by their v0.5 binary sort key.
7. For an edge whose endpoints are already in one component, record `ALREADY_CONNECTED` and do not run admission again.
8. Reject a union that would place a cannot-link inside one component.
9. Reject a union that introduces conflicting valid authoritative identity values across the two components.
10. Apply the V1 admission rule for the current component sizes.
11. On acceptance, merge union-find roots and all component metadata.
12. On rejection, retain a bounded review fact with the bridge, component summaries, and exact reason.
13. Emit memberships ordered by source sort key and union facts ordered by their processing sequence.
14. Validate that every active record appears once and no output component contains a cannot-link.

Use the smallest member source sort key as the union-find representative after every merge. Do not let rank, insertion order, hash-map iteration, UUID allocation, or query order select the representative.

## Component-admission contract

Implement this table exactly:

| Left and right components | Automatic admission |
|---|---|
| Two singletons | One identity edge or one strong edge |
| One singleton and one established component | One identity edge, or one strong edge plus another independent agreeing group that connects the singleton to the component |
| Two established components | A shared authoritative identity value, or at least two independent strong cross-component connections on distinct member pairs |

A component is established when it has more than one record.

For singleton-to-established admission, the additional group may come from supporting evidence. It must have another evidence-group name and disjoint compiled lineage. It may occur on the proposed edge or on another candidate pair between the singleton and the component.

For established-to-established admission, both connections must be strong, use independent groups with disjoint lineage, and involve different canonical member pairs. Two rules on one pair do not satisfy the rule.

Manual `MATCH` unions bypass automatic admission and authority conflicts, but never a `NOT_MATCH`. Strong disagreement alone is not a cannot-link.

## Component metadata

Maintain only data needed by admission and validation:

```text
sorted member source keys
component size
cannot-linked component roots
valid authoritative values by logical field
cross-component strong and supporting agreements indexed by member pair and group
smallest source key
```

After a union, merge the smaller metadata collection into the larger one. Every admission lookup iterates source keys, pairs, and groups in canonical order, regardless of the merge direction. Re-sort results at serialization. If component or check limits prevent a complete decision, return `MDM_RESOLVER_LIMIT`; never reject an edge merely because the check was expensive.

## Review and explanation facts

Return these stable rejection reasons for v0.7:

```text
CANNOT_LINK
AUTHORITATIVE_CONFLICT
SINGLETON_NEEDS_INDEPENDENT_GROUP
ESTABLISHED_NEEDS_TWO_STRONG_CONNECTIONS
ESTABLISHED_STRONG_CONNECTIONS_NOT_INDEPENDENT
ESTABLISHED_STRONG_CONNECTIONS_REUSE_PAIR
```

Bound member samples and value digests in each fact, but retain exact internal identifiers needed to recompute the decision. Candidate overflow and resolver-limit failures are operation errors, not review facts.

## Implementation order

1. Freeze `ResolverInput`, `Resolution`, reason codes, and fixture format.
2. Implement deterministic union-find and component metadata merges.
3. Apply manual closure and cannot-link checks.
4. Add authority-conflict checks.
5. Implement each row of the admission table as a pure function.
6. Process ordered automatic edges and serialize facts.
7. Add final invariants and fail-closed limits.
8. Add generated sequence, independent-oracle, and input-order property tests.
9. Run the labeled organization corpus and record cluster errors and review volume.
10. Extend `describe`, migrations, upgrades, and the tested operating envelope.

## Exit criteria

- [ ] The full-reference resolver implements every row of the V1 admission table.
- [ ] Manual closure, cannot-links, authority conflicts, and automatic edges use the documented precedence.
- [ ] Generated edge additions and removals equal clean full resolution at every step.
- [ ] The production union-find result equals the independent set-based oracle on generated small graphs.
- [ ] Input order, plan order, equal-ranked edge order, query plan, and UUID allocation do not change serialized results.
- [ ] Every successful result maps each active source record to exactly one component.
- [ ] No successful component contains a cannot-link.
- [ ] Every rejected plausible bridge has one stable reason and bounded diagnostic fact.
- [ ] Resource limits fail the operation instead of weakening an admission check or returning partial memberships.
- [ ] The resolver remains a pure Rust module with no SPI calls and no production output table.
- [ ] The domain-quality report and provisional resolver envelope meet their committed release thresholds.
- [ ] Upgrade tests and the complete v0.1 through v0.5 matrices pass.

## Deferred

Do not add incremental affected-set resolution, configurable clustering policies, stable IDs, merge or split commands, golden values, public memberships, parallel resolver workers, or checkpointing. Add an optimization only after it proves byte-equivalent to this resolver.

After this release, re-estimate v0.7 through v0.11 from measured clustering and component-check cost.
