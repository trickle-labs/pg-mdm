# v0.13 implementation plan: policy review projection

## Outcome

Implement M1 of `MDM-STEWARDSHIP/1`. An authorized pg-react reader can consume a
stable, logged MDM policy-case table with one positive bigint key per review
occurrence. MDM remains the only writer.

This release is read-only integration. It does not install automation bindings,
accept policy intents, change queue or deadline controls, or depend on pg-react
at runtime.

## Start gate

Require v0.12's admitted stack, accepted V1 evidence state, and signed shared
contract fixture. If the contract's columns, types, digest encoding, or opening
time rules remain disputed, do not create a provisional table.

## Public projection

Create the logged table `mdm_steward.policy_cases_v1`. It has this contract:

```text
case_key                    bigint primary key, positive
review_id                   uuid unique not null
entity_name                 name not null
issue_key                   bytea not null, 32 bytes
occurrence                  integer not null, positive
status                      text not null: open | resolved
severity                    text not null
reason_code                 text not null
approved_metadata           jsonb not null
permitted_actions           text[] not null
assigned_queue              name null
due_at                      timestamptz null
escalation_level            integer not null, nonnegative
manual_assignment_protected boolean not null
opened_at                   timestamptz null
opened_at_source            text not null: publication | administrator | unknown
resolved_at                 timestamptz null
review_version              bigint not null, positive
definition_version          bigint not null, positive
publication_revision        bigint not null, nonnegative
stewardship_epoch           bigint not null, nonnegative
evidence_basis_digest       bytea not null, 32 bytes
action_revision             bigint not null, positive
pending_stewardship         boolean not null
last_observed_at            timestamptz not null
```

Also require unique `(entity_name, issue_key, occurrence)` and a foreign key to
the retained internal review occurrence.

Reserve the three action names `ASSIGN_QUEUE`, `SET_DUE_AT`, and `ESCALATE`.
v0.13 projects their eligibility but does not execute them. Default controls are
no queue, no due date, escalation level zero, and no manual protection.
Every supported open occurrence permits the three administrative actions in
principle; every resolved occurrence permits none. Opening-time availability,
current controls, pending stewardship, and later binding limits decide whether a
specific request can apply.

Expose only `approved_metadata`, derived from the existing masked review summary
and an allowlist frozen in the contract. Do not expose `reviews.subjects`, raw
evidence, source keys, graph names, role OIDs, or private digests. Keep the table
free of RLS for the initial one-scope profile. Reject configuration that would
require an RLS-protected projection.

`SELECT` is not granted to `PUBLIC`. The administrator grants `USAGE` on
`mdm_steward` and `SELECT` on the table to the React policy role. The React role
gets no access to `mdm_internal` and no execute grant on human decision or golden
override functions.

## Durable identity and time

Use `mdm_internal.policy_case_key_seq` to allocate `case_key`. Register both the
table data and sequence state for logical dump. Never derive a bigint from the
UUID, recycle a key, or allocate a second key for the same `review_id`. Sequence
allocation is not transactional, so a rolled-back publication may leave a gap.
Gaps are valid and must never be filled by reusing a value.

When a review first enters the projection, derive `opened_at` by joining
`reviews.opened_revision` to `publications.published_at`. Set
`opened_at_source = publication`. On upgrade, apply the same rule to every retained
review occurrence. If the publication row is unavailable, preserve null and set
the source to `unknown`.

Add this function:

```text
mdm_admin.backfill_policy_case_opened_at(
    case_key bigint,
    opened_at timestamptz,
    reason text
) -> operation_id uuid, action_revision bigint
```

Require the entity execution role, a non-empty reason, an unknown current opening
time, and an instant no later than the first retained observation for the
occurrence. Record the authenticated session and selected role in
`mdm_internal.operations`. A backfill sets the source to `administrator` and
advances the action revision. It never changes the review's publication history.

Derive `resolved_at` from the matching publication when available. A missing
historical timestamp may remain null because it cannot authorize an automatic
action.

## Publication integration

Add one `project_policy_cases()` step inside `persist_refresh_inner()` after review
reconciliation and before output publication completes. Upsert evidence fields
and the latest successful observation fields in the same transaction as the MDM
publication or no-change observation.

For a changed publication, update a case's basis fields only when its evidence or
action tuple changes. `publication_revision` is the revision that established the
current case basis, not the entity's newest unrelated revision. For a no-change or
unrelated observation, update `last_observed_at`, `pending_stewardship`, and any
observation-derived freshness field without replacing the basis revision.

Compute `evidence_basis_digest` with the v0.12 canonical encoder and domain tag
`pg_mdm/policy-case-basis/v1`. Compare a canonical action tuple containing status,
reason, approved metadata, permitted actions, current controls, opening-time
availability, pending state, review version, definition version, stewardship
epoch, and the evidence digest. Increment `action_revision` only when this tuple
changes.

Set `pending_stewardship` by comparing the latest successful observation's
decision epoch with `entities.decision_epoch`. A failed refresh does not update the
projection. A later successful no-change refresh can clear pending state without
creating a new semantic publication.

When `decide`, `override_golden`, or `clear_golden_override` increments the entity
decision epoch, mark its open policy cases pending in the same transaction. Keep
their observed stewardship epoch and evidence basis unchanged until refresh.
Advance the action revision because automation eligibility changed. Put this in
one shared helper so later merge and split writes use the same rule.

Keep resolved occurrences in the table through restore and the future shared
replay horizon. A recurrence has a new `review_id`, `case_key`, `opened_at`, and
action revision starting at one.

## File layout

Use the existing schema, refresh, and security paths:

```text
src/
  policy.rs              canonical policy row and basis digest
  api/refresh.rs         publication-atomic projection call
  api/policy.rs          opening-time backfill helper and wrapper
  schema.rs              table, sequence, dump registration, ACLs
  error.rs               stable policy projection errors
  lib.rs                 module registration
tests/
  policy_tests.rs        pure digest and action-revision checks
  e2e_policy.sql         real publication, grants, rollback, and recurrence
```

Do not add a generic projection framework. One module and one publication hook
cover the contract.

## Upgrade and restore

Add the `0.12.0` to `0.13.0` migration. Backfill rows in deterministic
`entity_name`, `issue_key`, `occurrence` order so test fixtures receive stable
keys. Production consumers must treat the generated key as opaque and must not
depend on this ordering.

Register the public policy table and key sequence for logical dump. Extend
`sql/configure_helper.sql` to assign their owner to the helper role. A restored
projection remains read-only until the operator reapplies explicit reader grants.
Rebinding an entity must preserve case keys and timestamps.

Extend `mdm_admin.drop_entity()` to delete policy rows before the internal review
history. A failed drop leaves both intact. The existing explicit confirmation and
role checks remain unchanged.

Test upgrade from a populated v0.12 database with open, resolved, and recurring
reviews. Test clean logical restore into different relation and role OIDs. Compare
the exact policy rows before and after restore, excluding derived OIDs.

## Implementation order

1. Freeze the row codec and pure evidence-basis digest fixtures.
2. Add the table, sequence, dump registration, owner setup, and ACL checks.
3. Backfill existing review occurrences and opening times in the upgrade path.
4. Project changed publications, then no-change observations, in the refresh
   transaction.
5. Add the audited administrator backfill for unknown opening times.
6. Run the real pg-react R0 and R1 read path against the packaged extension.
7. Package 0.13.0 and run cumulative upgrade, restore, security, and E2E checks.

## Test matrix

| Case | Required result |
|---|---|
| First open occurrence | One positive key, publication opening time, exact tokens |
| Unchanged observation | Same key and action revision; observation state updates |
| Changed review evidence | Same key; review version, basis digest, and action revision advance |
| Resolution | Row remains, status becomes resolved, and automatic actions are absent |
| Recurrence | New UUID, key, opening time, and action revision |
| Unknown legacy opening | Null timestamp and no `SET_DUE_AT` permission |
| Authorized backfill | Timestamp commits once with an operation record |
| Failed publication | No policy row survives; any consumed key remains a gap |
| Reader privileges | Exact approved columns visible; private evidence remains denied |
| Shared-source CDC | React sees only committed policy rows after MDM publication |
| Restore and rebind | Keys, timestamps, digests, and occurrence mapping survive |
| Next key after restore | New occurrence receives a key above every restored key |
| FULL graph fallback | Policy output remains correct while affected graph nodes report FULL |

## Exit criteria

- [ ] `policy_cases_v1` matches the signed contract fixture by name, order, type,
  nullability, constraints, and allowed values.
- [ ] Each review occurrence has exactly one durable positive bigint key.
- [ ] Opening times come from retained publication evidence or an audited backfill.
- [ ] Failed publications and rolled-back backfills leave no visible changes.
- [ ] No-change observations update pending state without false policy work.
- [ ] The React reader passes against real MDM rows without private access or
  effects.
- [ ] Upgrade, logical restore, grants, masking, recurrence, and package checks
  pass on PostgreSQL 18 and pg-trickle 0.105.2.

## Deferred

Do not add bindings, intent submission, receipts, time evaluation, approvals,
identity automation, RLS policy sources, or multiple administrative scopes.
v0.14 adds only the three frozen control actions.
