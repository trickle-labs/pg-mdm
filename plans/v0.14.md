# v0.14 implementation plan: policy intents and receipts

## Outcome

Implement M2 of `MDM-STEWARDSHIP/1`. A bound automation role can request queue
assignment, a due date, or one escalation level. MDM validates the request and
commits the control change with one durable receipt.

Human decisions, golden overrides, publication, and identity remain separate.
`APPLIED_CONTROL` never means that MDM resolved or published an identity change.

## Start gate

Require the v0.13 policy table and a passing real React R1 read path. The signed
contract must fix request encoding, role behavior, action limits, terminal
outcomes, and the replay rule. Do not implement against a fixture-only policy
table.

## Binding model

Add durable `mdm_internal.policy_bindings` rows with:

```text
binding_id                  uuid primary key
entity_id                   uuid not null
binding_version             bigint not null, positive
automation_role_name        text not null
policy_digest               bytea not null, 32 bytes
allowed_actions             text[] not null
allowed_queues              name[] not null
max_due_interval            interval null
max_escalation_level        integer not null, nonnegative
created_at                  timestamptz not null
created_by_name             text not null
created_as_role_name        text not null
replaced_by                 uuid null
replaced_at                 timestamptz null
```

One unreplaced binding may exist for an entity and automation-role name. Arrays
are canonical, sorted, duplicate-free subsets of the three contract actions.
`max_due_interval` must be positive when `SET_DUE_AT` is allowed. The escalation
limit must be positive when `ESCALATE` is allowed. Empty queue lists make
`ASSIGN_QUEUE` invalid.

Keep runtime activation in derived `mdm_internal.policy_binding_runtime`:

```text
binding_id                  uuid primary key
database_oid                oid not null
automation_role_oid         oid not null
state                       text not null: active | paused
runtime_version             bigint not null, positive
changed_at                  timestamptz not null
```

Do not register runtime rows for logical dump. A clean restore therefore starts
disabled. A physical clone copies the row, but the database OID mismatch blocks
use. A role drop and same-name recreation also blocks use through the role OID
check. Restarting the same database preserves activation.

Add these administrator APIs:

```text
mdm_admin.create_policy_binding(
    entity_name text,
    automation_role_name text,
    policy_digest bytea,
    allowed_actions text[],
    allowed_queues text[],
    max_due_interval interval,
    max_escalation_level integer
) -> binding_id uuid, binding_version bigint

mdm_admin.replace_policy_binding(
    binding_id uuid,
    expected_version bigint,
    policy_digest bytea,
    allowed_actions text[],
    allowed_queues text[],
    max_due_interval interval,
    max_escalation_level integer
) -> binding_id uuid, binding_version bigint

mdm_admin.set_policy_binding_state(
    binding_id uuid,
    expected_runtime_version bigint,
    state text,
    reason text
) -> runtime_version bigint
```

The Rust-facing API accepts queue values as `text[]`, validates them, and stores
the canonical values in the durable `name[]` column.

The entity execution role creates and replaces bindings. Activation also requires
the named automation role to exist as `NOLOGIN`, `NOSUPERUSER`, and
`NOBYPASSRLS`, with no membership that reaches the helper or entity execution
role. A replacement creates a new inactive binding and permanently marks the old
one replaced. The operator activates the new binding only after React confirms
the exact policy digest and withdraws incompatible queued work.

Record each administration call in `mdm_internal.operations`. Never grant a
binding permission to `decide`, `override_golden`, `clear_golden_override`,
`refresh`, `rebuild`, merge, or split APIs.

Use expected runtime version zero when no runtime row exists. A successful state
change increments the runtime version. On an explicitly reconciled clone or
restore, the entity execution role may replace the stored database and role OIDs
through `set_policy_binding_state`; ordinary intent calls may not repair them.

## Human control API

Add a human-only control replacement function:

```text
mdm_steward.set_case_controls(
    case_key bigint,
    assigned_queue name,
    due_at timestamptz,
    escalation_level integer,
    manual_assignment_protected boolean,
    expected_action_revision bigint,
    reason text
) -> operation_id uuid, action_revision bigint
```

The entity execution role supplies the complete control tuple. Null queue or due
time clears that control. Validate queue syntax, a nonnegative escalation level,
an open case, optimistic concurrency, and a non-empty reason. Human changes are
not limited by an automation binding, but they remain bounded by PostgreSQL type
and configured entity limits. A human queue change with protection enabled
cannot be overwritten by automation until a later human call clears protection.

Update the policy row and operation record in one transaction. Increment the
action revision only when the control tuple changes. A no-op still records the
authenticated operation but does not manufacture policy work.

## Intent API

Install this exact public signature:

```text
mdm_steward.submit_policy_intent(
    binding_id uuid,
    request_key bytea,
    case_key bigint,
    action text,
    arguments jsonb,
    expected_review_version bigint,
    expected_definition_version bigint,
    expected_publication_revision bigint,
    expected_stewardship_epoch bigint,
    expected_evidence_basis_digest bytea,
    expected_action_revision bigint,
    expected_policy_digest bytea,
    policy_revision text,
    evaluation_ref text,
    work_ref text
) -> receipt_id uuid,
     outcome text,
     reason_code text,
     case_key bigint,
     action_revision bigint,
     control jsonb,
     resulting_publication_revision bigint
```

Require 32-byte request, evidence, and policy digests. Limit each reference to
256 UTF-8 bytes and reject empty values. `arguments` must contain only:

- `{"queue":"name"}` for `ASSIGN_QUEUE`;
- `{"due_at":"PostgreSQL timestamptz text"}` for `SET_DUE_AT`; or
- `{"level":positive_integer}` for `ESCALATE`.

Use PostgreSQL's timestamp input function after checking the exact key set. Reject
extra keys, null action values, and JSON numeric values outside `integer`.

Canonicalize the full request with encoding version 1 and domain tag
`pg_mdm/policy-intent/v1`. Persist the canonical body and its SHA-256 digest. Do
not accept caller-provided actor names, receipt outcomes, or timestamps.

## Receipts and idempotency

Create logged `mdm_steward.policy_receipts_v1` with one row per
`(binding_id, request_key)`. Store the receipt UUID, canonical request body and
digest, case key, action, outcome, reason code, old and new control values,
policy, evaluation, and work references, authenticated session and selected roles,
binding version, timestamps, and nullable resulting publication revision.

Keep receipts and request bodies without automatic deletion in this release.
Register them for logical dump. Any later pruning must add an explicit replay
horizon and an `OUT_OF_HORIZON` result before deletion ships.

Process a call in this order:

1. Validate the selected caller against the binding's stored role name and current
   role OID. Do this before reading a prior receipt.
2. If the request key exists, compare the canonical body digest. Return the prior
   receipt for an identical request, even when the binding is now paused or
   replaced. Return `MDM_IDEMPOTENCY_CONFLICT` for different bytes.
3. Lock the current binding row, then the case row. Use this lock order in every
   writer.
4. Validate runtime activation, replacement state, policy digest, case status,
   every expected token against the case basis, action permission, manual
   protection, and action limits. A newer unrelated entity publication is valid
   when the case's basis revision, evidence digest, and action revision did not
   change.
5. Apply either one control change or no change. Insert the receipt in the same
   transaction.

Malformed requests and unauthenticated callers raise stable MDM errors and leave
no receipt. Authenticated domain rejections create a terminal receipt with one of
these outcomes:

```text
APPLIED_CONTROL
NO_CHANGE
STALE_CASE
CASE_CLOSED
ACTION_DENIED
MANUAL_PROTECTION
OPENED_AT_UNKNOWN
LIMIT_EXCEEDED
BINDING_PAUSED
BINDING_REPLACED
POLICY_MISMATCH
```

`resulting_publication_revision` is null for every v0.14 action. Reserve
`ACCEPTED_PENDING_PUBLICATION` and `APPLIED_PUBLICATION` for a later contract that
can affect identity.

## Action rules

- `ASSIGN_QUEUE` requires an allowed queue and no manual assignment protection.
  Assigning the current queue returns `NO_CHANGE`.
- `SET_DUE_AT` requires a known `opened_at`. The due time must be no earlier than
  `opened_at` and no later than `opened_at + max_due_interval`. An existing due
  time stays unchanged unless the request explicitly supplies a different time
  under the active policy and current action revision.
- `ESCALATE` requires an open case, a due time no later than the transaction's one
  captured `statement_timestamp()`, and a requested level equal to the current
  level plus one. The level may not exceed the binding maximum.

Each applied action increments `action_revision` once. Receipt inserts, retries,
operation timestamps, and publication observations do not increment it. None of
these actions increments `decision_epoch`.

## File layout

```text
src/
  policy.rs              request codec, limits, and control transitions
  api/policy.rs          binding, human control, intent wrappers, and helpers
  schema.rs              binding, runtime, receipt schema, dump rules, ACLs
  error.rs               policy, stale, binding, and idempotency codes
  catalog.rs             role and database identity checks
tests/
  policy_tests.rs        canonical request and transition checks
  e2e_policy.sql         real-role transaction and receipt cases
```

Reuse `catalog::call_helper`, `validate_caller`, `operations`, and the existing
fixed search path. Do not add a command bus, workflow engine, or retry worker to
MDM.

## Upgrade and restore

Register durable bindings and receipts for logical dump. Keep binding runtime
derived. Extend `configure_helper.sql` with exact table and function owners.
Extend `mdm_admin.drop_entity()` to remove binding runtime, receipts, durable
bindings, and policy cases in dependency order. A failed drop preserves the
complete audit history. No other lifecycle operation deletes a request or receipt.

## Implementation order

1. Freeze canonical request vectors and pure control-transition tests.
2. Add durable bindings, derived activation rows, and administration APIs.
3. Add the human control API and manual assignment protection.
4. Add receipts and idempotent lookup before implementing effects.
5. Implement the three actions with locked token validation and atomic receipts.
6. Exercise the API through the actual React worker identity and transaction.
7. Add the `0.13.0` to `0.14.0` migration, owner setup, dump rules, and package
   archive.

## Test matrix

| Case | Required result |
|---|---|
| Identical retry | Same receipt and one control change |
| Same key, changed body | `MDM_IDEMPOTENCY_CONFLICT`, no mutation |
| Uncertain commit | Retry finds the committed receipt or reapplies nothing |
| Concurrent human edit | Stale terminal receipt; human value remains |
| Manual assignment protection | Automated queue change is denied |
| Paused or replaced binding | New request gets the exact terminal outcome |
| Prior retry after pause | Existing receipt still returns unchanged |
| Revoked or recreated role | Authorization fails before receipt disclosure |
| Policy digest change | Old queued work cannot apply |
| Deadline bounds | Unknown, early, and late deadlines fail closed |
| Escalation race | Only the next permitted level commits once |
| Outer transaction rollback | Control and receipt both disappear |
| Restore or clone | No new intent applies before explicit activation |
| Audit-only update | No action revision change |

## Exit criteria

- [ ] Only the three frozen actions can change policy controls.
- [ ] Every applied control and receipt commits atomically.
- [ ] Identical retries are idempotent and changed bodies conflict.
- [ ] All freshness and policy tokens are checked under the case and binding locks.
- [ ] Human protection, pause, replacement, restore, clone, and role recreation
  fail closed.
- [ ] The React worker can call only the intent API and can correlate the exact
  receipt in its own transaction.
- [ ] Cumulative security, upgrade, restore, package, and E2E checks pass.

## Deferred

Do not add automatic pair decisions, merge or split authority for the worker,
approval voting, business calendars, network delivery, or a generic action
registry. v0.15 qualifies this fixed integration on one named cohort.
