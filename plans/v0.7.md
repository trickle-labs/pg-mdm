# v0.7 implementation plan: identity and publication model

## Outcome

Turn one complete v0.6 resolution into durable entity IDs, golden values, reviews, explanations, and the three public output-table shapes. Preserve identity through no-change, merge, split, and mixed transitions. Apply public row changes and all supporting state in one transaction.

Use synthetic terminal evidence in tests. Do not create or advance a live `pg_trickle` graph in this release.

## Prerequisites and dependency changes

Start from v0.6 with complete memberships by `component_key`, accepted and rejected union facts, source-record identities, normalized values, pair evidence, and steward decisions.

Add no dependency. Use PostgreSQL 18 `uuidv7()` for new `mdm_id`, override, and review IDs. Use the existing `serde_json`, `sha2`, and `proptest` crates. Inject the UUID allocator into pure Rust reconciliation tests so fixtures remain repeatable.

Add the 0.6.0 to 0.7.0 migration and archive the generated 0.7.0 install SQL. Test upgrades from every earlier archived version.

```sql
CREATE TABLE mdm_internal.publications (
    entity_id uuid NOT NULL REFERENCES mdm_internal.entities(entity_id),
    publication_revision bigint NOT NULL CHECK (publication_revision > 0),
    definition_version bigint NOT NULL,
    decision_epoch bigint NOT NULL,
    operation_id uuid NOT NULL REFERENCES mdm_internal.operations(operation_id),
    source_boundary jsonb NOT NULL,
    source_boundary_digest bytea NOT NULL
        CHECK (octet_length(source_boundary_digest) = 32),
    result_digest bytea NOT NULL CHECK (octet_length(result_digest) = 32),
    published_at timestamptz NOT NULL DEFAULT statement_timestamp(),
    PRIMARY KEY (entity_id, publication_revision),
    FOREIGN KEY (entity_id, definition_version)
        REFERENCES mdm_internal.definitions(entity_id, definition_version)
);

CREATE TABLE mdm_internal.identity_registry (
    entity_id uuid NOT NULL REFERENCES mdm_internal.entities(entity_id),
    mdm_id uuid NOT NULL DEFAULT uuidv7(),
    created_revision bigint NOT NULL,
    retired_revision bigint,
    status text NOT NULL CHECK (
        status IN ('active', 'merged', 'split', 'retired')
    ),
    PRIMARY KEY (entity_id, mdm_id),
    CHECK (retired_revision IS NULL OR retired_revision >= created_revision),
    CHECK ((status = 'active') = (retired_revision IS NULL))
);

CREATE TABLE mdm_internal.memberships (
    entity_id uuid NOT NULL,
    source_record_id uuid NOT NULL,
    source_name name NOT NULL,
    source_id jsonb NOT NULL,
    mdm_id uuid NOT NULL,
    active boolean NOT NULL,
    first_membership_revision bigint NOT NULL,
    last_membership_revision bigint NOT NULL,
    membership_reason text NOT NULL,
    publication_revision bigint NOT NULL,
    PRIMARY KEY (entity_id, source_record_id),
    FOREIGN KEY (entity_id, source_record_id)
        REFERENCES mdm_internal.source_records(entity_id, source_record_id),
    FOREIGN KEY (entity_id, mdm_id)
        REFERENCES mdm_internal.identity_registry(entity_id, mdm_id),
    CHECK (last_membership_revision >= first_membership_revision)
);

CREATE TABLE mdm_internal.identity_aliases (
    entity_id uuid NOT NULL,
    alias_mdm_id uuid NOT NULL,
    canonical_mdm_id uuid NOT NULL,
    publication_revision bigint NOT NULL,
    PRIMARY KEY (entity_id, alias_mdm_id),
    FOREIGN KEY (entity_id, alias_mdm_id)
        REFERENCES mdm_internal.identity_registry(entity_id, mdm_id),
    FOREIGN KEY (entity_id, canonical_mdm_id)
        REFERENCES mdm_internal.identity_registry(entity_id, mdm_id),
    CHECK (alias_mdm_id <> canonical_mdm_id)
);

CREATE TABLE mdm_internal.identity_splits (
    entity_id uuid NOT NULL,
    parent_mdm_id uuid NOT NULL,
    child_mdm_id uuid NOT NULL,

        entity_id,
        parent_mdm_id,

        publication_revision

    FOREIGN KEY (entity_id, parent_mdm_id)
        REFERENCES mdm_internal.identity_registry(entity_id, mdm_id),
    FOREIGN KEY (entity_id, child_mdm_id)
        REFERENCES mdm_internal.identity_registry(entity_id, mdm_id)
);
```

Add the anchored override ledger:

```sql
CREATE TABLE mdm_internal.golden_override_directives (
    override_id uuid PRIMARY KEY DEFAULT uuidv7(),
    entity_id uuid NOT NULL REFERENCES mdm_internal.entities(entity_id),
    field_name name NOT NULL,
    anchor_source_record_id uuid NOT NULL,
    action text NOT NULL CHECK (action IN ('SET', 'CLEAR')),
    value jsonb,
    value_type oid,
    override_version bigint NOT NULL CHECK (override_version > 0),
    reason text NOT NULL CHECK (length(btrim(reason)) > 0),
    created_by oid NOT NULL,
    created_at timestamptz NOT NULL DEFAULT statement_timestamp(),
    supersedes uuid REFERENCES mdm_internal.golden_override_directives(override_id),
    superseded_by uuid REFERENCES mdm_internal.golden_override_directives(override_id)
        DEFERRABLE INITIALLY DEFERRED,
    UNIQUE (
        entity_id,
        field_name,
        anchor_source_record_id,
        override_version
    ),
    FOREIGN KEY (entity_id, anchor_source_record_id)
        REFERENCES mdm_internal.source_records(entity_id, source_record_id),
    CHECK (
        (action = 'SET' AND value IS NOT NULL AND value <> 'null'::jsonb
            AND value_type IS NOT NULL)
        OR
        (action = 'CLEAR' AND value IS NULL AND value_type IS NULL)
    )
);

CREATE UNIQUE INDEX golden_overrides_one_current_anchor
    ON mdm_internal.golden_override_directives (
        entity_id,
        field_name,
        anchor_source_record_id
    )
    WHERE superseded_by IS NULL;
```

Use the same update order as `steward_decisions`: set the old row's deferred `superseded_by`, then insert the new row. Increment `decision_epoch` for either action.

Keep resolution facts and golden provenance for the current and immediately previous semantic publication. Retain the identity registry, aliases, split links, current memberships, override directives, and review occurrences for their full V1 lifetime.

Keep all internal tables inaccessible to non-extension roles.

## Stable-ID reconciliation

Use the previous active memberships as the identity ledger. Reconcile all components together:

1. For each previous `mdm_id`, find its active old members that still occur in the new resolution.
2. Pick the member with the smallest `first_membership_revision` as that ID's continuity anchor. Break ties with the canonical source-record sort key.
3. Let the new component containing the anchor claim the old ID.
4. If a new component has no claims, allocate one new `mdm_id` with `uuidv7()`.
5. If a new component has one claim, retain that ID.
6. If a new component has several claims, retain the ID with the earliest `created_revision`. Break a tie by UUID byte order.
7. Map every old ID to the final IDs of all new components containing any of its old members.
8. If an old ID maps to itself only, keep it active.
9. If an old ID maps to one different ID, mark it merged and add one alias.
10. If an old ID maps to several IDs, add every successor to `identity_splits`. Keep the registry status active when one successor retains the old ID. Otherwise, mark it split. Do not represent the split as a simple alias.
11. If an old ID maps to no active component, mark it retired.

This anchor rule covers isolated merges and splits and gives mixed merge-and-split transitions one deterministic result. Resolve alias chains transitively, reject cycles, and retain every historical link.

## Golden-value selection

Select each field independently from active component members. The input record carries the raw value, normalized value, source name, source priority, optional `row_changed_at`, authority flag, and source sort key.

Implement these policies exactly:

| Policy | Order |
|---|---|
| `prefer_source` | Declared source priority, greatest available row-change time, then source sort key |
| `latest` | Greatest required row-change time, declared source priority, then source sort key |
| `first_non_null` | Declared source priority, then source sort key |
| `most_common` | Greatest normalized-value count, greatest authoritative-contributor count, source priority, then canonical normalized bytes |

For `most_common`, choose the published spelling from the highest-priority contributing record, then break a tie by source sort key. Emit `GOLDEN_TIE` when the top normalized values share the greatest count before later tie breaks. Emit `INVALID_AUTHORITATIVE_VALUE` for an invalid authoritative candidate.

Apply active anchored overrides before a built-in policy. If one component contains different active override values for a field, publish SQL `NULL` with `override_conflict` status and emit `GOLDEN_OVERRIDE_CONFLICT`. Equal overrides agree and use the oldest directive, then directive UUID order. If an anchor is inactive, use the built-in policy and emit `GOLDEN_OVERRIDE_ANCHOR_INACTIVE`.

Validate an override against the declared PostgreSQL type before storing it. JSON null is not a value. Use `clear_golden_override()` to remove an override.

## Review reconciliation

Build `issue_key` as SHA-256 over the issue-key format version, definition version, reason code, and canonical subject identities. Do not include display text or raw sensitive values.

For each publication:

1. Keep a matching open issue unchanged when its severity, subjects, and summary are unchanged.
2. If that payload changes, update it, set the new `publication_revision`, and increment `concurrency_version`.
3. Resolve an open issue that no longer occurs.
4. For an issue that recurs after resolution, insert a new `review_id` with `occurrence = previous + 1`.
5. For a changed definition or changed canonical subject set, create a different issue key.

Create reviews for ambiguous supporting-only pairs, authority conflicts, rejected bridges, golden ties, invalid authoritative values, inactive override anchors, override conflicts, and split notices. Treat candidate and resolver limit failures as operation errors, never reviews.

## Publication transaction

Publish synthetic test input with the same boundary that v0.9 later wraps around live graph refresh:

1. Lock the entity row and acquire its transaction advisory lock.
2. Pin the desired definition, base publication revision, and `decision_epoch`.
3. Load current identity, membership, override, golden, and review state.
4. Reconcile IDs, select golden values, and reconcile reviews in memory.
5. Validate active membership uniqueness, identity links, public schema compatibility, typed golden values, and output referential integrity.
6. Compute one canonical result digest over the definition, memberships, IDs, aliases, splits, goldens, reviews, and retained facts.
7. If the digest equals the active result, return `changed = false` without a new semantic revision.
8. Otherwise, insert the publication and supporting history, apply the logical public-table diff, activate the desired definition, update the entity revision, and commit together.

An injected error after any write must roll back the internal ledger and all three public outputs. v0.9 adds `refresh_graph_strict()` before step 3 in the same outer transaction.

## Exit criteria

- [ ] New, unchanged, merged, split, retired, and mixed transitions follow stable-ID policy 1.
- [ ] Every retired merge ID resolves through an alias, and every split retains all successors without a simple alias.
- [ ] Rebuild and replay with the original ledger preserve all required IDs.
- [ ] All four golden policies and anchored overrides produce deterministic typed values and complete provenance.
- [ ] Review issue keys and occurrence numbers remain stable under replay and input reordering.
- [ ] `mdm.explain()` returns bounded, masked, machine-readable facts for every supported subject and identity state.
- [ ] The three logged public table shapes have stable names, golden column order, and PostgreSQL types.
- [ ] Publication uses row-level diffs. It does not use `TRUNCATE` or relation swaps.
- [ ] A no-change result creates no semantic publication or public row changes.
- [ ] Any failed write rolls back identity, membership, golden, review, fact, and public output changes together.
- [ ] Generated histories produce byte-identical memberships, goldens, reviews, explanations, and result digests under replay and input reordering.
- [ ] No live `pg_trickle` graph, private catalog access, affected-set resolution, or output-delta consumer exists.
- [ ] Upgrade tests and the complete v0.1 through v0.6 matrices pass.

## Deferred

Do not add live graph creation, `mdm.refresh()`, `mdm.preview()`, `mdm_admin.rebuild()`, direct merge or split commands, coherent record-level golden selection, a semantic change feed, or explanation beyond the retained V1 range. Add those only in their roadmap release.
