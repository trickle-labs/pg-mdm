# v0.7 implementation plan: identity and publication model

## Outcome

Turn one complete v0.6 resolution into durable entity IDs, golden values, reviews, explanations, and the three public output-table shapes. Preserve identity through no-change, merge, split, and mixed transitions. Apply public row changes and all supporting state in one transaction. Deliver the release through four separately reviewed internal gates.

Use synthetic terminal evidence in tests. Do not create or advance a live `pg_trickle` graph in this release.

## Prerequisites and dependency changes

Start from v0.6 with complete memberships by `component_key`, accepted and rejected union facts, source-record identities, normalized values, pair evidence, and steward decisions.

Add no dependency. Use PostgreSQL 18 `uuidv7()` for new `mdm_id`, override, and review IDs. Use the existing `serde_json`, `sha2`, and `proptest` crates. Inject the UUID allocator into pure Rust reconciliation tests so fixtures remain repeatable.

Add the 0.6.0 to 0.7.0 migration and archive the generated 0.7.0 install SQL. Test upgrades from every earlier archived version.

Use the same one-way predecessor contract as `steward_decisions`: mark the old row non-current, then insert the new current row with `supersedes` set to the old ID. A deferred constraint trigger enforces the same entity, field, and anchor across the chain and requires `is_current` exactly when no successor exists. Increment `decision_epoch` for either action.

Use the v0.5 audit contract for both `SET` and `CLEAR`. Record the authenticated actor, selected role, operation ID, base publication revision, and resulting epoch in the same transaction as the directive. Base revision zero means that nothing has been published yet.

Keep resolution facts and golden provenance for the current and immediately previous semantic publication. Retain the identity registry, aliases, split links, current memberships, override directives, and review occurrences for their full V1 lifetime.

Register every table in this section, including `publication_observations`, with `pg_catalog.pg_extension_config_dump()`. The one-way supersession links keep the dump dependency graph restore-safe. Store portable role and PostgreSQL type names in durable rows. Resolve OIDs during binding and DDL, and keep them only in derived source or graph bindings. Public output tables are rebuildable projections and are not configuration data.

Runtime-created public tables remain ordinary objects included by normal `pg_dump`; do not attach them to the extension to suppress their DDL or data. A restore validates and reuses restored outputs against the durable ledger. Create a projection only if it is absent, and fail on a conflicting shape or owner. Preserve restored ACLs, indexes, triggers, dependent views, and replica identity. Do not drop and recreate an existing output during recovery. The clean-restore test must include these consumer objects as well as row contents. This uses PostgreSQL's [extension configuration-table rules](https://www.postgresql.org/docs/18/extend-extensions.html#EXTEND-EXTENSIONS-CONFIG-TABLES).

Keep all internal tables inaccessible to non-extension roles.

## Stable-ID reconciliation

Use the previous active memberships as the identity ledger. Reconcile all components together:

1. For each previous `mdm_id`, find its active old members that still occur in the new resolution.
2. Pick the member with the smallest `first_membership_revision` as that ID's continuity anchor. Break ties with the canonical source-record sort key.
3. Let the new component containing the anchor claim the old ID.
4. If a new component has no claims, allocate one new `mdm_id` with `uuidv7()`.
5. If a new component has one claim, retain that ID.
6. If a new component has several claims, retain the ID with the earliest `created_revision`. Break a tie by UUID byte order.
7. Map every old ID to the final IDs of all new components containing any of its old members.
8. If an old ID maps to itself only, keep it active.
9. If an old ID maps to one different ID, mark it merged and add one alias.
10. If an old ID maps to several IDs, add every successor to `identity_splits`. Keep the registry status active when one successor retains the old ID. Otherwise, mark it split. Do not represent the split as a simple alias.
11. If an old ID maps to no active component, mark it retired.

This anchor rule covers isolated merges and splits and gives mixed merge-and-split transitions one deterministic result. Resolve alias chains transitively, reject cycles, and retain every historical link.

Apply cycle rejection to alias-only chains. Split history includes the parent-to-self successor when that ID survives. A split followed by a remerge can also contain `A -> B` at one revision and `B -> A` at a later revision. Traverse historical transitions by increasing publication revision, using `(mdm_id, revision)` as the traversal state, and deduplicate current successors. Do not interpret the combined links as an unversioned acyclic graph. Return the registry's current status separately from split history and its resolved successor set. Bound returned facts without silently truncating identity resolution; if its work limit is exceeded, return a resource error.

## Golden-value selection

Select each field independently from active component members. The input record carries the raw value, normalized value, source name, source priority, optional `row_changed_at`, authority flag, and source sort key.

Implement these policies exactly:

| Policy | Order |
|---|---|
| `prefer_source` | Declared source priority, greatest available row-change time, then source sort key |
| `latest` | Greatest required row-change time, declared source priority, then source sort key |
| `first_non_null` | Declared source priority, then source sort key |
| `most_common` | Greatest normalized-value count, greatest authoritative-contributor count, source priority, then canonical normalized bytes |

For `most_common`, choose the published spelling from the highest-priority contributing record, then break a tie by source sort key. Emit `GOLDEN_TIE` when the top normalized values share the greatest count before later tie breaks. Emit `INVALID_AUTHORITATIVE_VALUE` for an invalid authoritative candidate.

Apply active anchored overrides before a built-in policy. If one component contains different active override values for a field, publish SQL `NULL` with `override_conflict` status and emit `GOLDEN_OVERRIDE_CONFLICT`. Equal overrides agree and use the oldest directive, then directive UUID order. If an anchor is inactive, use the built-in policy and emit `GOLDEN_OVERRIDE_ANCHOR_INACTIVE`.

Validate an override against the declared PostgreSQL type before storing it. JSON null is not a value. Use `clear_golden_override()` to remove an override.

## Review reconciliation

Build `issue_key` as SHA-256 over the issue-key format version, definition version, reason code, and canonical subject identities. Do not include display text or raw sensitive values.

For each publication:

1. Keep a matching open issue unchanged when its severity, subjects, and summary are unchanged.
2. If that payload changes, update it, set the new `last_change_revision`, and increment `concurrency_version`.
3. Resolve an open issue that no longer occurs.
4. For an issue that recurs after resolution, insert a new `review_id` with `occurrence = previous + 1`.
5. For a changed definition or changed canonical subject set, create a different issue key.

Create reviews for ambiguous supporting-only pairs, authority conflicts, rejected bridges, golden ties, invalid authoritative values, inactive override anchors, override conflicts, and split notices. Key a split notice by parent ID, complete successor set, and split publication. Open it only in the publication that first records the split, resolve it on the next semantic publication, and do not recreate it merely because split history remains. Remove it from the public retention window only during a later semantic publication; age alone never creates a revision. Keep the internal occurrence. A later distinct split gets a new issue key. Treat candidate and resolver limit failures as operation errors, never reviews.

## Publication transaction

Publish SQL-backed synthetic test input with the same boundary that v0.9 later wraps around live graph refresh. Use a deterministic boundary object containing the fixture and terminal-relation digests; v0.9 replaces it with the real Graph V1 boundary.

1. Lock the entity row and acquire its transaction advisory lock.
2. Pin the desired definition digest, compiled-artifact digest, base publication revision, and `decision_epoch`.
3. Load current identity, membership, override, golden, and review state.
4. Reconcile IDs, select golden values, and reconcile reviews in memory. Preserve split notices and retained facts whose cleanup depends only on the prospective revision.
5. Validate active membership uniqueness, identity links, public schema compatibility, typed golden values, and output referential integrity.
6. Compute the canonical publication projection over the selected definition, memberships, active and retired IDs, aliases, splits, golden values and provenance, review state, and retained explanation facts. Exclude the compiled artifact, source boundary, observation ID, operation ID, timestamps, concurrency counters, prospective revision number, and row last-change markers. Before any persistence, recheck the pinned definition, artifact, base publication revision, and decision epoch.
7. If the digest equals the active result, insert only a `publication_observations` row for the new boundary and return `changed = false`. Do not create a semantic revision or perform public-table DML.
8. Otherwise, apply split-notice resolution and retention cleanup permitted by the new revision, then compute the final projection and stored digest. Insert the publication, observation, and supporting history; apply only public payload diffs; activate the desired definition; and update the entity revision in the caller's transaction. Verify the expected final definition, artifact, decision epoch, revision, and actual public payload after output triggers have run. The caller commits or rolls back that transaction.

A changed winning source or retained explanation fact creates a semantic publication even when membership and the visible golden value stay equal. The logical public diff may still be empty. Evidence, compiled-artifact, or later graph-binding changes that do not change the retained projection create only an observation.

Do not resolve a split notice or prune facts before step 7 merely because another refresh was attempted. Repeated identical refreshes after a split remain observations, even across a retention-age boundary. Once another semantic change qualifies a revision, its final digest includes the permitted cleanup, and the following unchanged refresh is again an observation.

Every successful observation records the pinned `decision_epoch`, including the no-change path. `describe()` compares the current epoch with the latest successful observation when reporting pending stewardship work. The immutable publication's original epoch does not describe later no-change validation.

Reject reentrant publication for the same entity. Entity locks are reentrant within one transaction and do not prevent a consumer trigger from calling back into MDM. If a trigger changes pinned state, suppresses an output write, or changes the planned payload, fail and roll back the complete publication. Audit triggers whose writes preserve the planned result remain supported.

An injected error after any write must roll back the internal ledger and all three public outputs. v0.9 adds `refresh_graph_strict()` before step 3 in the same outer transaction.

## Test matrix

| Level | Case | Expected result |
|---|---|---|
| Unit | New and unchanged components | New gets one UUID; unchanged keeps its ID |
| Unit | Two components merge | Earliest-created ID survives; the other becomes an alias |
| Unit | One component splits | The continuity-anchor child keeps the ID; every other child gets a new ID |
| Unit | Mixed merge and split transition | The anchor-claim algorithm returns one deterministic assignment |
| Unit | Alias chain and attempted cycle | Resolution is transitive; the cycle is rejected |
| Unit | Split, remerge, split again; alias followed by a split | Current successors are complete and deduplicated; historical traversal terminates despite valid self-links and later reverse links |
| Unit | Removed and reactivated source record | The tombstone and first-membership revision survive |
| Unit | Every golden policy and tie break | The selected value and provenance match the fixture |
| Unit | Golden tie and invalid authoritative value | Selection is deterministic and the expected review is emitted |
| Unit | Equal, conflicting, inactive-anchor, replaced, and cleared overrides | Status, value, review, and version follow the contract |
| Unit | Issue remains, disappears, recurs, or changes definition | The occurrence stays, resolves, increments, or gets a new key |
| Unit | Split notice first appears, survives the split publication, and reaches the next semantic publication | It opens once, then resolves without recurring from retained split history |
| Property | Shuffle every input collection | IDs, memberships, goldens, reviews, facts, and digest stay identical |
